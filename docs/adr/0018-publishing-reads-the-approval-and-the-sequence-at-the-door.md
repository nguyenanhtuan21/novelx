# Publishing reads the approval and the sequence at the door

ADR-0001 makes Human Approval the public-publishing gate and ADR-0017 makes it a condition of the Quality Gate. Together they leave a chapter that cannot be published: the gate's best outcome is every condition green with `humanApproval` outstanding, and approving happens afterwards, so the result on the draft still names `humanApproval` as blocking when an operator goes to publish. Reading the stored result literally would refuse every chapter a reviewer just signed off.

So the publishing door drops `humanApproval` from what the last run found and reads the approval itself. This is safe because it is the same check with a fresher answer: the gate answers that condition by looking at `draft.humanApproval`, so it is the one condition of the seven that publishing can re-run without re-reading the prose. Every other condition is a judgement about the draft as the gate found it, and only a new run can change one — a blocking `policySafety` is still blocking however recently someone approved the chapter.

Approving is its own permission. `chapter:approve` is separate from `chapter:write` and from `chapter:publish`, so writing a Chapter, taking accountability for it, and putting it in front of readers can be held by three people. This is the same argument ADR-0017 made for `chapter:quality-gate`: an approval is only worth what the separation behind it is worth, and an editor who can approve their own prose has signed nothing. NovelX does not yet refuse an approval from whoever authored the draft, because the author is in the ledger rather than on the Chapter; naming the gap rather than implying it is closed.

A reviewer may only answer the condition that is theirs. Approving a draft the gate blocked for any other reason is refused, and so is approving one the gate has never run on, which keeps approval as the last condition of the gate rather than a way around the rest of it. Approving an already-approved draft changes nothing, like locking a Story Bible: the approval names who took the decision, and a second one must not move that to whoever pressed the button most recently.

Publishing is in sequence, read from what readers can already see. A Chapter cannot go out before the one ahead of it, and a Chapter already published is refused rather than given a second version — a change to public text is a revision, which carries a reason this does not. The Chapter numbers come from the published record rather than from the request, because whether a Series is in order is a fact about the Series and not a claim its publisher can make about it. Two operators publishing at once can both pass that check, so the repository writes a version once and answers whether it wrote; the second one is told the Chapter is already published rather than quietly overwriting what readers saw.

A schedule is an intention, not a publication. It says when an approved Chapter may go out, and publishing before then is refused; nothing here publishes on its own, and an operator or a later worker still does the publishing. Only a Chapter that could be published now can be scheduled, so a schedule is a decision about *when* rather than a promise to finish the gates later. Scheduling changes no content, so it leaves a Staff Audit Record and no line of lineage: ADR-0016 appends lineage where content changes, and an intention is an operation.

This closes the gap ADR-0015 and ADR-0017 both recorded. `assertPublishableDraft` no longer asks the draft for a `rightsRecordId` and a `provenanceLedgerEntryId` as bare strings nobody resolved — those are conditions of the Quality Gate, which looks the grant up against the records and asks the ledger for the draft's lineage. Keeping the string check as well would have put the weaker test last, and neither string was ever set by any route through the CMS, so publishing through the API was impossible in exactly the way an unresolved id is worthless.

What a Published Snapshot carries follows from that. It names every grant that cleared the Chapter for publishing rather than one — a Chapter routinely draws on several licensed materials, and picking one of them would be arbitrary — and the lineage entry its content traced when it went public, rather than the entry the draft happened to be authored under. Both are read off the records at the moment of publishing, so what a reader can see stays answerable afterwards.

A Chapter id names a Chapter everywhere it is used, so the CMS now refuses a draft id another Series already holds. It was previously checked within one Series, which meant authoring under a second Series did not create a second Chapter — it moved the first, silently, because the store is keyed by that id and so is the Published Snapshot named after it.

The remaining hole is a draft edited after it was approved. There is no route that edits a draft's prose today, so it cannot happen yet; when the CMS grows one, an edit has to clear the approval and the gate result together, for the same reason ADR-0017 gives for re-running the gate after an edit.
