# Lineage is appended where content changes

ADR-0008 makes an internal append-only ledger the source of truth for how chapter text and AI workflow artifacts were made. It does not say where entries are written, and NovelX already has a trail that looks close enough to reuse.

It is not the same trail. The Staff Audit Record answers whether the boundary let somebody act; the Provenance Ledger answers how the content got to be what it is. Two consequences follow, and they point in opposite directions. A refused staff operation belongs in the audit trail and leaves no provenance, because nothing was made. An AI workflow run belongs in the ledger as a source in its own right, even though it can never be a Staff Account (ADR-0005) and so can never appear as a staff actor. Merging the two would force one of those facts to be recorded as the other. So they stay apart, and a governed write leaves a line in each.

Entries are appended by the CMS service after the write is held, not by the staff gate that authorised it. The gate is the right place for attempts, which is exactly why it is the wrong place for lineage: it runs before the work, so it cannot know what the work produced. The cost is that a write which lands and then fails to append leaves content with no lineage. That is the honest trade for the MVP — the alternative is a transaction spanning the CMS store and the ledger, which is worth doing when the ledger is what a Quality Gate reads rather than what an editor reads.

Each entry carries the version context of what it traces: canon entry ids for a Story Bible, chapter number and cleared Rights Record ids for a draft Chapter, the snapshot version for a publish. Ids rather than content, because the CMS holds the content and a copy in the ledger would drift from it. The version context is tagged with the same kind as the target and refused when they disagree, since lineage pointing at the wrong content is worse than none.

Reading lineage needs `provenance:read`, separately from `audit:read` and from `series:read`. Who shaped the catalog and how is a different question from what the catalog says, and an editor who may write a Series is not thereby someone who may read the history of every AI workflow that touched it. Reads append nothing: a ledger that grew a line each time somebody looked would bury the content history under the reading of it.

The publishing path is not wired here. `publishChapter` exists in the domain but nothing in the API calls it yet, so the ledger knows the `published-snapshot` target kind and can build the version context for one, and the publishing ticket owns appending the entry. `ChapterDraft.provenanceLedgerEntryId` stays what it was — the entry a Published Snapshot points at — and authoring a draft does not fill it. Filling it with the authoring entry would let a draft satisfy the publishing gate's provenance condition by having been written, which is the one thing that condition is meant to rule out.
